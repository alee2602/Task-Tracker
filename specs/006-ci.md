# Spec 006: CI con GitHub Actions

Estado: IMPLEMENTADO (verificación de ejecución real pendiente, ver abajo)
Plan: [plans/006-ci-plan.md](../plans/006-ci-plan.md)

## Problema

Ahora mismo "verificación" en cada ciclo significa que yo corro `pytest` a mano
antes de cerrar el spec. No hay nada que corra los tests automáticamente cuando
se sube código, así que es fácil que un cambio rompa algo sin que nadie se dé cuenta
hasta la próxima vez que alguien corra los tests manualmente.

## Objetivo

Un workflow de GitHub Actions que corra la suite de tests automáticamente.

## Alcance (dentro)

- Workflow que corre `pytest` en:
  - cada push a `main`
  - cada Pull Request
- Prueba contra Python 3.12 (una sola versión, no matriz).
- Badge de estado ("passing"/"failing") en el `README.md`.

## Fuera de alcance (por ahora)

- Matriz de múltiples versiones de Python.
- Linting/formateo automático (ej. `ruff`, `black`) como parte del CI.
- Reporte de cobertura de tests.
- Publicación/deploy automático (ej. a PyPI).

## Decisiones

Ninguna decisión de arquitectura nueva que amerite ADR: es configuración estándar
de GitHub Actions para un proyecto Python con `pyproject.toml` + `pytest`.

## Criterios de aceptación

- [ ] Un push a `main` dispara el workflow y corre los tests.
- [ ] Un Pull Request dispara el workflow y corre los tests.
- [ ] El workflow falla visiblemente si algún test falla.
- [ ] El `README.md` muestra el badge de estado del CI.

## Verificación

YAML validado con un parser (estructura correcta). Los pasos del workflow
(`pip install -e ".[dev]"`, `pytest`) son los mismos comandos ya usados y
verificados manualmente en los 5 ciclos anteriores. **Pendiente**: la primera
ejecución real solo se puede confirmar después de hacer push a GitHub —
revisa la pestaña "Actions" del repo tras el push para verificar que corrió
y pasó.
